## Configure Without Leaking Secrets

REST uses `WORKCHORD_BASE_URL`, an optional API prefix, and
`AGENT_API_KEY`. Agent routes are normally below `/api`; avoid accidentally
constructing `/api/api/...`.

MCP HTTP normally uses `/api/mcp` and either a bearer token or
`X-Agent-API-Key`; stdio uses `MCP_AGENT_API_KEY`. Use a real enabled actor key,
not `AGENT_BOOTSTRAP_API_KEY`. Keep all values in the runtime secret store.

## Prefer Stable V1 Operations

Confirm these exact stable-v1 operations in the live capability contract before
autonomous work:

| Operation | REST/MCP contract |
| --- | --- |
| Capabilities | `GET /api/agent/capabilities`; `agent_get_capabilities` |
| Current/next work | `GET /api/agent/me/work?limit={n}&cursor={opaque}` with private ETag/`304`; `agent_get_my_work(limit, cursor)` |
| Complete context | `GET /api/agent/tasks/{task_id}/context?assignment_id={assignment_id}`; `agent_get_complete_task_context` |
| Active claims/runs | `GET /api/agent/me/claims`, `GET /api/agent/me/runs`; `agent_list_my_claims`, `agent_list_my_runs` |
| Begin | `POST /api/agent/me/work/begin`; `agent_begin_my_work` |
| Renew | `POST /api/agent/me/work/renew`; `agent_renew_my_work` |
| Progress events | claim-bound `/api/agent/tasks/{id}/events` or assignment-bound `/api/agent/runs/{id}/events`; `agent_append_task_event` or `agent_append_run_event`; use only `agent.progress`, `agent.checkpoint`, or `agent.blocker` |
| Discovery | `POST /api/agent/discoveries`; `agent_report_discovery` |
| Submit | `POST /api/agent/me/work/submit`; `agent_submit_my_work` |
| Fail/cancel | `POST /api/agent/me/work/fail`; `agent_fail_my_work` |

Do not invent endpoint names for actions the capability response does not
advertise. Do not simulate atomic begin/submit with a client-side wrapper and
call it v1.

### Use model-aware begin only when enforced

The generated `model-aware-begin` row freezes the conditional payload on the
same atomic begin route/tool. Use it only when the live capability response
advertises `model-aware-routing-v1`, reports
`model_aware_routing.effective_mode=enforced`, the assignment/context select an
explicit binding, and the live OpenAPI/MCP metadata matches the generated row.
Send the assignment's exact `model_binding_id` and
`model_binding_revision` plus the runtime's observed `resolved_model_id`; these
are not client choice fields.

Do not fall back to the base begin shape after accepting a model-aware
assignment. Missing, stale, unavailable, or mismatched binding/model evidence
requires a fresh authoritative read and `attention_required` handoff. When the
feature is absent or effective mode is `off` or `shadow`, the base assigned-work
lifecycle may remain autonomous for legacy assignments if all of its own
required features are present, but no WorkChord model-selection or
model-verification claim is allowed.

## Use Supervised V0 Compatibility Primitives Carefully

An older or intentionally compatibility-only deployment may expose:

| Method | Path | Scope | Use |
| --- | --- | --- | --- |
| `GET` | `/api/agent/tasks/ready` | `tasks:read` | Check readiness for an explicit handoff; never choose global work |
| `POST` | `/api/agent/tasks/{id}/claim` | `tasks:write` | Claim one explicit task |
| `POST` | `/api/agent/tasks/{id}/renew` | `tasks:write` | Renew its lease |
| `POST` | `/api/agent/tasks/{id}/release` | `tasks:write` | Release its lease |
| `PATCH` | `/api/agent/tasks/{id}` | `tasks:write` | Patch only worker-owned status with `expected_version` |
| `POST` | `/api/agent/tasks/{id}/events` | `events:write` | Append a bounded task event |
| `POST` | `/api/agent/runs` | `runs:write` | Start a task-bound run |
| `POST` | `/api/agent/runs/{id}/events` | `runs:write` | Append a run event |
| `POST` | `/api/agent/runs/{id}/finish` | `runs:write` | Finish as `succeeded`, `failed`, or `canceled` |

These compatibility routes are not the stable assigned-worker lifecycle. Do not
fall back to them after a v1 assignment/fence conflict.
An actor whose explicit scope list contains `work:execute` is a v1
assigned-work actor, and the server rejects legacy claim, renew, release,
run-start, and run-finish calls for it. Supervised-v0 compatibility requires a
separately provisioned legacy actor without `work:execute`; never change scopes
yourself.

The corresponding MCP compatibility tools are:

- `agent_list_ready_tasks` and `agent_get_task_context`;
- `agent_claim_task`, `agent_renew_claim`, and `agent_release_task`;
- `agent_patch_task` and `agent_append_task_event`;
- `agent_start_run`, `agent_append_run_event`, and `agent_finish_run`.

Prefer `agent_report_discovery` in v1. It binds the Triage record to the current
assignment, run, task version, and live fence under `triage:write`. General
workspace Triage tools are PM planning surfaces and are not a worker fallback.

Derive a discovery retry key such as
`discovery:<external-run-id>:<task-id>:<stable-finding-key>`, where the final
component is stable for the same finding. If `triage:write` is absent, autonomous
v1 is not fully compatible with this skill: do not call a broader endpoint.
Return the bounded finding to the caller/PM channel and continue only when it is
non-blocking and the accepted criteria remain valid.

Use `agent_get_task_context` for the task plus merged timeline. Do not use
workspace planning tools to reassign, reprioritize, reschedule, decompose, or
close the worker's task.

## Supply Mutation Inputs

| Mutation | Required worker inputs |
| --- | --- |
| V1 begin | assignment ID, queue revision, lease request, trace/run metadata, idempotency key; the server revalidates the assignment-bound task version |
| V1 renew | assignment ID, run ID, task version, current claim ID/generation, lease request, idempotency key |
| V1 event/write | assignment/task, live claim/fence, supported version fields, trace, idempotency key |
| V1 discovery | assignment, task/version, running run, live claim/fence, classification, bounded evidence, idempotency key, and `triage:write` |
| V1 submit/fail/cancel | assignment/task/version, claim/fence, run, evidence/outcome, idempotency key |
| V0 claim/renew | explicit task ID, lease, deterministic idempotency key |
| V0 patch | explicit task ID, latest `expected_version`, status-only payload, deterministic idempotency key |
| V0 task event | explicit task ID, event payload, trace/correlation, deterministic idempotency key |
| V0 run start | explicit task ID, trace/run metadata, deterministic idempotency key |
| V0 release | explicit task ID, deterministic idempotency key |

Stable task events require the HTTP `Idempotency-Key` or matching MCP argument.
Assignment-bound run events carry idempotency key, claim ID, and claim
generation in their payload. The legacy run-finish
primitive does not expose a durable request fingerprint; stable v1 uses atomic
submit/fail instead. After an ambiguous response, read state before any retry
and escalate if the outcome cannot be proven.

## Use Minimal V0 Payloads

Claim/renew REST body:

```json
{
  "lease_seconds": 3600,
  "trace_id": "external-run-id",
  "span_id": "claim-or-renew",
  "correlation_id": "handoff-id"
}
```

Worker status patch:

```json
{
  "expected_version": 7,
  "status": "active"
}
```

Task progress event:

```json
{
  "event_type": "agent.progress",
  "payload": {
    "summary": "Completed the first acceptance checkpoint.",
    "next_steps": ["Run the documented verification"]
  },
  "trace_id": "external-run-id",
  "span_id": "checkpoint-1",
  "correlation_id": "handoff-id"
}
```

Run finish:

```json
{
  "status": "succeeded",
  "summary": "Implemented the assigned scope and recorded verification evidence.",
  "artifact_links": ["https://artifact.example.invalid/result/123"]
}
```

Use real approved artifact URLs at runtime; never copy example hosts or include
credentials. Keep task patches narrow so an execution worker cannot overwrite
PM-owned fields accidentally.

## Verify Every Mutation

After each call, accept returned versions, expiry, claim/run state, and task
status as authoritative. Re-read the affected context before the next mutation.
Handle REST and MCP errors according to
[events-errors-and-recovery.md](events-errors-and-recovery.md). Never switch
actors or transports to bypass a permission, conflict, or lifecycle error.

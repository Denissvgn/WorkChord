# Identity and recovery

## Choose the access mode

`WORKCHORD_AUTH_MODE=managed` is the default. Ordinary APIs require a verified human session, a native bearer session, or an enabled agent credential with the appropriate membership. Missing provider configuration shows a setup message and denies private API access.

`WORKCHORD_AUTH_MODE=trusted_local` explicitly enables open collaboration for a trusted, isolated workspace. The account menu labels this mode. It is a deployment setting, never selected automatically when sign-in fails. Operator settings and recovery still require operator credentials. Restart every replica consistently when changing modes.

For managed sign-in, register an OIDC confidential client using authorization code flow. Configure `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, and the exact `OIDC_REDIRECT_URI`, such as `https://work.example/api/auth/callback`. The provider must support PKCE S256 and RS256 ID tokens with a published signing key ID. Discovery issuer, audience, signature, nonce, expiry, browser state, and return URL are checked. Use HTTPS, `SESSION_COOKIE_SECURE=true`, and an exact `CORS_ORIGINS` JSON allowlist. Configure the reverse proxy not to log callback query strings or credential headers. Provider keys and subject identifiers are authoritative; email, IP address, and display name never prove identity.

The development-only `OIDC_ALLOW_HTTP_LOOPBACK` option permits loopback and the isolated issuer hostname `oidc`; production ignores it. Do not enable it for a shared deployment. Compose passes the identity settings to the web process. Apply the normal migration service, then the dedicated repairs service, before starting web replicas; repairs initialize the operator control-plane identity. Schema-only transfer targets intentionally remain empty.

## Establish ownership and grant access

1. Set a strong `WORKCHORD_ADMIN_API_KEY` through your deployment's secret store. This key represents an audited system operator. Keep it separate from `AGENT_BOOTSTRAP_API_KEY`.
2. Sign in once. `/api/auth/me` returns the new durable principal ID even before membership is granted.
3. From an operator client without a conflicting browser cookie, POST `/api/auth/bootstrap` with `X-Admin-API-Key` and `{"principal_id":123}`. This can establish the first owner only once. It cannot replace an existing owner.
4. Use PUT `/api/auth/project-members/{project_id}/{principal_id}` with `{"role":"editor","reason":"Approved team membership"}`. Roles are viewer, editor, executor, reviewer, or manager. Use `role:null` to revoke. Only workspace operators or the project's manager may administer that project.
5. Link a verified human to a work profile using PUT `/api/auth/principals/{principal_id}/profile`, `{"profile_id":456,"reason":"Confirmed profile ownership"}`. A profile links to at most one human principal. The owner account menu also provides explicit profile linking. Profile and iteration capacity rows remain separate from login identity.

Workspace PUT `/api/auth/workspace-members/{principal_id}` accepts owner, operator, member, or null with a reason. A workspace member can collaborate on unscoped work; it does not confer access to private projects. Global profile metadata, calendar definitions, credentials, and integration settings are operator managed. A linked human can select their own availability calendar and manage their versioned absences in My Work; project access alone does not grant private absence detail. Reviewers can accept project work, executors cannot. A person who performed work needs another reviewer; an operator can explicitly supply `X-Review-Override:true` and `X-Command-Reason` for accountable self-review. The command audit retains that decision. Legacy closed work with unknown review provenance remains unknown.

Read results are scoped on the server, including child records and snapshot payloads. Scheduling a shared iteration requires access to its entire input graph. A partial authorized graph cannot be scheduled as though it were complete. Public plan links expose a frozen projection, expire after 30 days, and can be revoked. Existing links with no historical expiry remain revocable. Intake and GitHub webhook exceptions require their own configured token or signature and execute under a verified system identity. Restricted agent onboarding acknowledgements verify the exact handoff credential before acquiring integration authority; that credential cannot use ordinary agent APIs while onboarding. Principal account disablement and actor runtime enablement remain separate, so onboarding never revives an explicitly disabled principal. Public skill bundles retain their checksum requirement; see [role-package delivery](external-agent-runtime.md#provision-and-connect).

## Sessions, guest data, and recovery

Human sessions last eight hours by default (`AUTH_SESSION_MAX_AGE_SECONDS=28800`). Cookies are opaque, HttpOnly, and SameSite=Lax. Browser mutations require `X-CSRF-Token` from `/api/auth/me` and an allowed Origin when present. Native clients exchange an authenticated session at POST `/api/auth/native-token`, then use `Authorization: Bearer`. Different principals in cookie, bearer, admin, or actor credentials cause rejection.

The Android companion connects through a browser-approved handoff. It starts POST `/api/auth/native-connections/start` with an S256 proof challenge, displays the verification code, and opens the returned `/mobile/connect` path on the configured server. Sign in through the workspace's trusted provider, compare the code, and explicitly approve the connection. The app then calls POST `/api/auth/native-connections/exchange` with its private verifier to obtain a native bearer session. Connections expire after ten minutes and can be consumed once; approval is checked again against the enabled human account and unrevoked browser session. The verifier and native session stay on the device rather than in the browser URL. Use HTTPS outside explicitly selected local debug builds. Release builds start without a server address and require an explicit workspace origin. Cleartext is denied; local HTTP is restricted to localhost, 127.0.0.1 and the emulator host in debug builds. Redirects are disabled for authenticated API traffic. Native bearer sessions, cookies, sign-in proofs and explicitly saved private drafts use device Keystore encryption in storage excluded from backup. The human companion does not store or send agent API keys. Logout removes credentials and saved drafts for the current account; expiry quarantines drafts until that account signs in and verifies access again. Server/account changes clear private views and current authorization. Release network logging is disabled; debug logging excludes headers and bodies.

GET `/api/auth/sessions` lists the account's sessions; DELETE `/api/auth/sessions/{public_id}` revokes one. POST `/api/session/rotate` replaces the cookie while preserving principal ownership. POST `/api/auth/logout` revokes the current session. PUT `/api/auth/principals/{principal_id}` with `{"enabled":false,"reason":"Account recovery requested"}` disables the account and revokes its sessions. Reenabling does not revive tokens. Recover provider access through the trusted provider, then grant/relink only after verifying the same durable identity or documenting an operator decision. Never edit identity-subject rows based on matching names.

The web shell partitions cached work by account and access grants. Task drafts can recover in the same browser tab and account for up to 24 hours; sign-out or account change clears them. After an interrupted save, compare the current task before reapplying. Eligible live work views refetch on focus and every 30 seconds while foregrounded, with bounded backoff to four minutes after failures. Hidden, disabled and unauthorized polling stops. Editor snapshots and immutable history do not poll. Automatic refresh is limited to at most five accumulated pages; larger retained windows require an explicit read. Account/access replacement cancels old work requests and clears their cache. Refresh failures display stale state without replacing an unsaved draft.

Guest views and shares require proof. After signing in from a valid guest session, choose **Bring my guest views and shares**, or POST `/api/auth/transfer-guest` with the current `guest_token`. Knowing a guest session ID alone is insufficient. An operator can recover abandoned data using `guest_session_id`, the verified destination `principal_id`, and a reason. Transfer preserves the original anonymous attribution, records an ownership-transfer audit, revokes the guest token, and rotates public share links. Repeating the same completed transfer is safe.

Schedule POST `/api/auth/sessions/cleanup` from an operator client. Each call processes at most 500 eligible sessions. Expired/revoked metadata older than `SESSION_METADATA_RETENTION_DAYS` (default 30 days) is anonymized; referenced rows and historical audit remain. Expired login attempts are removed in bounded batches. Identity writes, including cleanup and rotation, honor maintenance fences. Session IP/user-agent metadata is persisted until cleanup; this is pseudonymous operational data.

## Application snapshots

Successful commands save one bounded pre-change recovery point per affected iteration in `application_snapshots`. Default limits are ten records per iteration and 8 MiB per payload. Domain writes, revisions, history, recovery retention, and outbound jobs commit together. Failed commands and previews cannot publish or evict recovery points. Delivery workers send queued external events after commit.

GET `/api/iterations/{id}/snapshots` lists authorized recovery points; GET the filename under that path to inspect one. Records survive container replacement and replicas because they are stored in the database. They cover supported iteration/task/allocation planning state. Restoring one iteration preserves current shared person calendars, absences, and delivery prerequisites. Remove incoming delivery links explicitly before a restore that would delete their targets. Retained discussion is associated with the original task identity. They do not cover the whole workspace, credentials, provider configuration, external artifacts, or external side effects. Actual-event/audit evidence and acceptance are distinct: restore invalidates current acceptance and records a deliberate restoration of baseline dates.

For a restore, drain writers and inspect the source point and current iteration revision. POST `/api/iterations/{id}/snapshots/{filename}/restore` with `{"confirm":true,"expected_revision":17}` using operator credentials. A conflict requires inspection of current state. Recover active claims first. The command preserves supported IDs, writes a pre-restore point and audit, and refuses unknown identity/provenance or incompatible project scope. Compare tasks, dependencies, capacity, absences, and dates afterward. Use the pre-restore point for a scoped reversal when safe.

Restore recovers the saved allocation membership. Later safe allocations are detached from that iteration while their IDs and global references remain intact. External task or live execution references must be reconciled first; unsupported allocation-reference ownership prevents restoration. Shared person profiles, calendars, availability and absences remain current.

Legacy files are never silently trusted. Mount the old snapshot directory read-only at `data/snapshots/{iteration_id}` relative to the backend working directory and POST `/api/iterations/{id}/snapshots/import-legacy` with `{"dry_run":true,"limit":25}`. Review checksums, shape, and disposition; `dry_run:false` records the bounded provenance inventory. Ambiguous preview-era files are quarantined for explicit reconciliation, not offered as trustworthy restore points. Keep the original files and full backup for operator recovery.

## Backup and deployment rollback

An application snapshot is not a database backup or authorization to release autonomous production work. Use the existing [database runtime policy](database-runtime-policy.md) and deployment backup/restore commands for checksummed logical/base backups and isolated full restores. Backups and supported database transfer include identity, ownership history, and application snapshot tables. Keep the encryption key and deployment/provider configuration recoverable separately.

Before upgrading, capture a full database backup and pin the running image/configuration. Restore into an isolated target with the matching supported schema and verify identities, memberships, task IDs, and snapshot checksums before replacing a replica. Container replacement with the same database must retain the same snapshot inventory. Never point a restore exercise at a live database. The additive identity migration deliberately rejects destructive downgrade; rollback uses the previous full database backup with its matching application image after writer drain. Do not drop identity or audit tables to make an old binary start. Preserve the new database copy if newer changes need reconciliation.

## Compatible revision checks

Task responses expose `version` and their observed `iteration_revision`. Create, delete, merge, unmerge, reorder, batch, and schedule commands accept the corresponding expected revision. Bulk and schedule previews return their input versions for apply. A supplied stale version returns a structured 409; inspect or recalculate before reapplying. The web task, Board, bulk, and Gantt flows carry these revisions and preserve drafts after conflict.

`STRICT_MUTATION_VERSIONS=false` keeps compatibility while callers adopt observed revisions. Set it to `true` only after every supported deployment and integration supplies the required fields. Missing inputs then return HTTP 422 / MCP `mutation_revision_required`, naming the field and the capabilities endpoint. Supplied stale inputs continue to return structured conflicts. Web operator credentials do not bypass these checks; dedicated offline migration/repair process roles retain their existing authorization and resource limits.

Use `expected_version` for task commands, `expected_revision` for one iteration, and `expected_revisions` for every affected iteration in multi-scope/shared-input commands. REST callers can also send a bounded `X-Expected-Revisions` JSON map (at most 500 positive iteration IDs/revisions and 16,384 characters), including on routes without a body. Body and header values must agree. This context grants no permissions. The text editor reads `/api/iterations/{id}/tasks/text-context` and retains that revision with its draft; a conflict requires comparison before reapplying.

Older planning forms may still omit revisions and must remain on a compatibility deployment until upgraded. Missing-revision counters are process-local observations; collect them across replicas and a stated observation window before deciding adoption is complete. Absence of a scrape is not zero traffic. Rolling the flag back to `false` preserves authorization and supplied-version conflict checks. Global calendar/profile changes still reserve and snapshot every affected scheduling aggregate. Pure structural rearrangements preserve accepted leaf evidence and inherited optional/deferred meaning; content changes invalidate acceptance.

# WorkChord 1.9.0

Version 1.9.0 follows the 1.1 interface release. It brings team project managers
into day-to-day dispatch, makes review independence and task replacement auditable,
reconciles GitHub pull requests with the work that was submitted, and adds dated
capacity transfers and a date-move preview. It also adds the operator tooling for
coordinated maintenance windows, WAL archive retention and self-hosted adoption.

The notes below group the changes by outcome. Pull request numbers link to the
change on GitHub.

## What changed for people

### Team project managers can dispatch work

A team project manager can select a ready worker and dispatch eligible work to them,
within the team. Reassignment checks both the old and the new owner. Work outside the
manager's team is not shown and cannot be assigned.
([#74](https://github.com/Denissvgn/WorkChord/pull/74),
[#102](https://github.com/Denissvgn/WorkChord/pull/102))

A project manager who is not yet bound to a team now gets a clear status: the server
reports that the caller is not bound, that its roster scope is empty, and what the
operator should do next. Previously this was a bare refusal.
([#93](https://github.com/Denissvgn/WorkChord/pull/93))

Routing previews show only the requesting team's actors. A focused preview for a named
worker or reviewer keeps that actor's rows even when the response has to truncate other
rows, so a manager can see why a specific person was or was not chosen.
([#102](https://github.com/Denissvgn/WorkChord/pull/102),
[#108](https://github.com/Denissvgn/WorkChord/pull/108),
[#109](https://github.com/Denissvgn/WorkChord/pull/109))

### Model-aware routing and planning packets

Routing previews are bounded. The preview is built as the same validated response that
REST and MCP return, and it is trimmed only until the complete response fits the stored
size limit. The recommended candidate is always kept. Clients must return the server's
`preview_digest` when they act on a preview.
([#78](https://github.com/Denissvgn/WorkChord/pull/78),
[#109](https://github.com/Denissvgn/WorkChord/pull/109))

A team manifest can declare tool capabilities for a model binding. A declared
capability is recorded for review but is not trusted: routing reads only the binding's
own verified tags, so a missing tool still blocks assignment until the operator
confirms it. ([#105](https://github.com/Denissvgn/WorkChord/pull/105))

Planning reconciliation refuses malformed evidence digests the same way on REST and
MCP. An operator can bind a seed key to an existing planning profile that has none,
keeping its capacity rows, assignments and history attached.
([#94](https://github.com/Denissvgn/WorkChord/pull/94),
[#97](https://github.com/Denissvgn/WorkChord/pull/97))

### Independent review and verification

When a project requires a reviewer from a different model publisher, the reviewer must
be independent of every run that contributed to the task, including interrupted and
reworked runs. ([#75](https://github.com/Denissvgn/WorkChord/pull/75))

An operator can deliver an immutable review packet to one specific verifier and record
a receipt for it. The receipt binds the reviewed commit and the packet's SHA-256 digest,
and for source-and-test review, each test result. A receipt expires within 24 hours and
can be revoked. ([#76](https://github.com/Denissvgn/WorkChord/pull/76))

Removing a capacity allocation that nothing uses no longer disturbs work that has
already been issued. A proven unused allocation is deleted, and issued work keeps its
version. ([#77](https://github.com/Denissvgn/WorkChord/pull/77))

Verification previews keep the implementation profile of a shadow-mode compatibility
dispatch, so independent reviewers are no longer excluded only because that profile was
unknown. ([#111](https://github.com/Denissvgn/WorkChord/pull/111))

The carried review history of a replacement task is walked with a fixed depth and size
bound. When the bound is reached, the check fails closed and the review is refused with a
clear reason. ([#117](https://github.com/Denissvgn/WorkChord/pull/117))

Reassigning a verification that has a receipt is done by cancelling and recreating the
verification. The runbook describes the checks and keeps the prior evidence.
([#90](https://github.com/Denissvgn/WorkChord/pull/90))

### Task replacement

A task whose earlier runs cannot be attributed to a model publisher cannot be accepted,
and a new run on the same task does not fix that. A project manager can now replace such
a task with a clean replacement. The decision is recorded: who decided, when and why, the
immutable base commit, the runs whose commits are carried over, and the dependents and
releases that moved.

- The original task is withdrawn as replaced work. It keeps its runs, artifacts and
  attribution, and it can never be reviewed, accepted or reopened.
- Its schedule and delivery dependents move to the replacement.
- The replacement is planned, with no runs or assignments, and it is the single
  deliverable that is counted.
- Only the project's manager, a workspace operator or the project's PM actor may decide.

([#114](https://github.com/Denissvgn/WorkChord/pull/114))

### GitHub pull requests and catch-up

A task's linked pull request now reflects what the worker submitted: the submitted
commit, the observed head and its checks, the target branch, the merge commit once the
pull request has merged, the time of observation, the review state, and the next
accountable role. Webhook deliveries and manual refreshes share one observation, and an
older delivery that arrives late can no longer roll a link back.
([#116](https://github.com/Denissvgn/WorkChord/pull/116))

A catch-up reads the task's own pull requests from GitHub for events a deployment never
received. An outside merge or an unmerged closure is recorded on the task timeline.
Catch-up never accepts or closes a task; acceptance stays with the independent reviewer.
([#116](https://github.com/Denissvgn/WorkChord/pull/116))

The public gateway now routes the agent connect discovery document to the server, so
role packages no longer receive the web page when they look for the server.
([#87](https://github.com/Denissvgn/WorkChord/pull/87))

### Capacity transfers and dated adjustments

A capacity row can have an availability that applies only on specific dates. Two rows of
the same person that overlap on a day no longer require lowering one row for its whole
iteration. ([#103](https://github.com/Denissvgn/WorkChord/pull/103))

A project manager can lend part of one person's availability, from one or more rows, to
that person's row in another project for a bounded date range. Each source keeps its own
share minus what it lends, and the target gains what it receives. The rows' own
percentages do not change, so the prior shares apply again the day after the transfer
ends, with no scheduled job. A preview shows the percentage and hours before and after
for each row and date, and nothing is saved until the transfer is applied.

A transfer is refused when the lent time is in use by issued work, when the rows belong
to different profiles, when it would lend more than a row's own share, when the dates fall
outside the iteration, when it overlaps an active adjustment, or when it starts in the
past. Withdrawing a transfer returns every row together; dates that have already passed
keep what was lent. ([#113](https://github.com/Denissvgn/WorkChord/pull/113))

### Iteration date-move preview

Before a project manager moves an iteration's dates, they can preview the move against
the shared capacity of every person involved. The preview shows who would be overbooked
on the new dates in their other projects, and it changes nothing.
([#110](https://github.com/Denissvgn/WorkChord/pull/110))

### Schedules, Gantt and project fixes

- The Gantt iteration shows its owning project, as the iteration view already did.
  ([#89](https://github.com/Denissvgn/WorkChord/pull/89))
- A saved schedule that starts a task on or before its prerequisite ends is flagged in
  readiness and on the Gantt, so Schedule no longer reads as done while such a pair
  exists. ([#96](https://github.com/Denissvgn/WorkChord/pull/96))
- A schedule run says which tasks it cleared, and a task held back by an undated
  predecessor also shows its own cause, such as a missing owner.
  ([#88](https://github.com/Denissvgn/WorkChord/pull/88))
- Assignment lists can be read completely through a paged listing.
  ([#91](https://github.com/Denissvgn/WorkChord/pull/91))

### Pipeline and work status

Active work that was delivered outside a WorkChord run now appears in the pipeline, in
its own stage, "Active outside a run", with its accountable owner. The stage offers no
recovery action; recovery still needs a recovery signal or a claim.
([#98](https://github.com/Denissvgn/WorkChord/pull/98))

A rework or recovery assignment that has begun shows as started in the task context, and
it no longer lists blockers that apply only to work not yet begun.
([#100](https://github.com/Denissvgn/WorkChord/pull/100))

The run detail shows the execution provenance stored with the run, in both REST and MCP.
Historical unknowns stay unknown. ([#86](https://github.com/Denissvgn/WorkChord/pull/86))

A feature-only runtime re-acknowledgement no longer ends an extended work window, so work
keeps its owner after an upgrade. ([#107](https://github.com/Denissvgn/WorkChord/pull/107))

Pages that load lazily no longer stall while the work refresh status updates.
([#112](https://github.com/Denissvgn/WorkChord/pull/112))

The Android companion's Compose, navigation and coroutine libraries are updated.
([#81](https://github.com/Denissvgn/WorkChord/pull/81),
[#82](https://github.com/Denissvgn/WorkChord/pull/82))

## What changed for PMs and agents

### Skill packages

| Role package | Version in this release | Version in 1.1 |
| --- | --- | --- |
| `workchord-pm` | 1.21.5 | 1.16.0 |
| `workchord-worker` | 1.20.3 | 1.16.0 |
| `workchord-reviewer` | 1.8.5 | 1.4.0 |

The skill catalog is at version 1.23.5. The PM package covers verification rework, the
cancel-and-recreate route for a different verifier, the roster rule for an unbound PM,
the task replacement and GitHub reconciliation routes, and the delivery prerequisite
guidance below. The reviewer package has a note for reviewing a change that is merged on
another branch. ([#115](https://github.com/Denissvgn/WorkChord/pull/115),
[#125](https://github.com/Denissvgn/WorkChord/pull/125))

### Delivery prerequisites on a target branch

A delivery prerequisite can name the branch that must contain the predecessor's code.
Readiness reads the stored pull request observation of the predecessor and never calls
GitHub itself. When the code is not observed on that branch, the task waits, and the next
owner is the PM, who runs catch-up. A merge alone does not accept a task: a release needs
an accepted predecessor whose merge commit has been observed on the named branch.
Ordinary dependencies behave as before. ([#125](https://github.com/Denissvgn/WorkChord/pull/125))

### API additions

All of the following are additive. Existing requests keep working.

- `GET /api/agent/assignments/page` returns assignments in pages, with `has_more` and
  `next_cursor`.
- `POST /api/tasks/{task_id}/delivery-dependencies` accepts an optional `target_branch`.
- `GET /api/tasks/{task_id}/github-reconciliation` reads the reconciliation, and
  `POST /api/tasks/{task_id}/github-reconciliation/catch-up` runs a scoped catch-up.
- Task replacement: `POST /api/tasks/{original_id}/replacement` and `GET` on the same
  path, with the agent planning routes and MCP tools.
- Capacity transfers: `POST /api/team-capacity-transfers/preview` and
  `POST /api/team-capacity-transfers`, with the withdrawal routes and MCP tools.
- Iteration date move: `POST /api/iterations/{iteration_id}/date-move/preview` and its
  MCP tool.
- Routing previews accept `focus_actor_id` and `focus_model_binding_key` to keep one
  named actor's rows in a bounded preview.
- Team status responses carry `caller_binding`, `roster_scope` and `feature_advertised`.
- `POST /api/team-member-profiles/{id}/seed-key` binds a seed key to an existing profile,
  once, for operators only.

Check the current API schemas when you update a client.

### Maintenance windows for agents

A long-running worker can keep its live claim through a coordinated restart, but only when
the claim's owner acknowledges the window. Agents read the open window with
`GET /api/agent/me/maintenance-windows/current` and acknowledge it with
`POST /api/agent/me/maintenance-windows/{id}/acknowledge`. A lease or a quiet period is
never taken as consent. ([#99](https://github.com/Denissvgn/WorkChord/pull/99))

## What changed for operators

### Coordinated maintenance windows

A release that restarts a server other people use follows the
[maintenance window runbook](../runbooks/control-plane-maintenance-window.md). Admission
for new claims closes when the window is announced. A window begins only when every live
claim is acknowledged by its owner, every lease lasts past the planned outage, and every
active project manager has a notice receipt. When the window completes, each protected
claim is recorded as preserved, finished or lost. ([#99](https://github.com/Denissvgn/WorkChord/pull/99))

### WAL archive retention

The database's WAL archive now has a retention rule. A `wal-archive-retention` service
runs the pruning script every six hours by default (`WAL_PRUNE_INTERVAL_SECONDS`). It
removes archived WAL that point-in-time recovery no longer needs, anchored on the newest
verified base backup. With no verified backup it removes nothing, and it refuses to run
when the backup's start segment is not in the archive.
([#92](https://github.com/Denissvgn/WorkChord/pull/92))

The retention service starts with `docker compose up -d`. Take a fresh base backup first,
then review what would be removed with a dry run before the first prune:

```
docker compose run --rm --no-deps wal-archive-retention /bin/bash /opt/workchord/prune_wal_archive.sh --dry-run
docker compose run --rm --no-deps wal-archive-retention /bin/bash /opt/workchord/prune_wal_archive.sh
```

The rule and the recovery window are described in the
[backup and restore runbook](../runbooks/postgresql-backup-restore.md).

### Self-hosted adoption and deployment record

A running compose project can be moved into the self-hosted layout in its own folder,
keeping its database and credential sink contents. The
[self-hosted adoption runbook](../runbooks/self-hosted-adoption.md) covers the
preconditions, an isolated rehearsal, the cold copy with digest checks, acceptance,
rollback and retirement of the old project.

Each deployment can write a `deployment-record.json` with
`scripts/server/write_deployment_record.py`. The record names the image references, the
immutable image IDs and registry digests of every service, the source revision and tag,
the WorkChord version, the compose project and its volumes, and the deployment it
replaces. It contains no secrets. ([#126](https://github.com/Denissvgn/WorkChord/pull/126))

### Long databases and the migration path

Migrating a database with a long retained history no longer stops at a row limit. The
project-identity check reads every retained row in pages and keeps its protections: a
migration that would be unsafe refuses before any schema change, and a refusal changes no
data. The [PostgreSQL operations guide](../runbooks/postgresql-operations.md#upgrading-a-database-with-a-long-retained-history)
covers rehearsal on an isolated restore, dropping any carried patch, the refusal codes and
rollback from the verified backup. ([#101](https://github.com/Denissvgn/WorkChord/pull/101),
[#85](https://github.com/Denissvgn/WorkChord/pull/85))

### Gateway

The production gateway routes the agent connect discovery document to the server. Reload
the gateway after the upgrade. ([#87](https://github.com/Denissvgn/WorkChord/pull/87))

### Wiki replay and lock tooling

A maintainer preflight, `scripts/ci/wiki_lock_root_preflight.py`, reports the lock root the
wiki writer will use and exits non-zero when it differs from the checkout's own Git
directory. The full-reconstruction profile for replaying the wiki from a canonical checkout
is described in [local development](../local-development.md).
([#95](https://github.com/Denissvgn/WorkChord/pull/95),
[#104](https://github.com/Denissvgn/WorkChord/pull/104))

## Upgrade notes

### Database migrations

This release adds four migrations, applied in order:

- `20261124_0021`: maintenance windows and their receipts.
- `20261124_0022`: dated capacity adjustments.
- `20261124_0023`: task replacements.
- `20261124_0024`: the delivery prerequisite target branch.

A downgrade of `20261124_0024` is refused while any delivery prerequisite names a target
branch. Clear those target branches before a downgrade is attempted.

On a populated database, the migration runs the complete project-identity check before
any schema change. A database already at head starts without that scan. Rehearse the
upgrade on an isolated restore first, following the
[PostgreSQL operations guide](../runbooks/postgresql-operations.md#upgrading-a-database-with-a-long-retained-history).

### Before the upgrade

1. Take a verified base backup.
2. On a server that other people use, announce a maintenance window and follow the
   [maintenance window runbook](../runbooks/control-plane-maintenance-window.md).
3. Upgrade the backend and frontend images to 1.9.0.
4. Start the WAL archive retention service, then run the dry run and the prune shown above.

### Backend dependency floor

The backend requires `pydantic>=2.11`, because the code uses the `exclude_if` field option
added in that version. The backend lock file is refreshed for this change and keeps
pydantic 2.13.4.

### Role skill packages

Reinstall the role packages at the versions in the table above, checking each SHA-256
digest against the skill catalog entry. If your workspace already runs these versions,
nothing needs to be reinstalled. The setup steps for each runtime are in
[agent team setup](../agent-team-setup.md).

# WorkChord 1.10.0

Version 1.10.0 follows the 1.9.0 release. It makes GitHub pull request state easier to
trust: a merge or closure is recorded once, an accepted task stays accepted when its code
is merged, and a task page shows the reconciliation for each linked pull request and lets
an editor set the target branch of a delivery prerequisite. It adds MCP tools and a REST
route for the same operations, and it moves the self-hosted acceptance evidence store from
MinIO to Versity S3 Gateway. It also brings the Android and frontend toolchains up to date,
including Tailwind CSS 4.

The notes below group the changes by outcome. Pull request numbers link to the change on
GitHub.

## What changed for people

### GitHub pull requests stay accurate

A merge or closure of a linked pull request is recorded once on the task timeline, whichever
catch-up or webhook delivers it first. ([#132](https://github.com/Denissvgn/WorkChord/pull/132))

An observed merge no longer makes an accepted task look stale. When the pull request head is
still the commit that was submitted, acceptance is kept, and the timeline records that it was
preserved. A head that moved after acceptance still needs review.
([#139](https://github.com/Denissvgn/WorkChord/pull/139))

A catch-up over a task with several linked pull requests now records the observation of every
link, not only the last one. ([#137](https://github.com/Denissvgn/WorkChord/pull/137))

### Reconciliation on the task page

The task page has a reconciliation panel in Work and review. For each linked pull request it
shows the submitted commit, the observed head (flagged when it differs), the checks, the target
branch, the merge or closure, the time of the observation, the differences and the next owner.
Replacement and successor tasks appear there too. People with edit access can run a catch-up
from the panel. ([#138](https://github.com/Denissvgn/WorkChord/pull/138))

Each delivery prerequisite on the task page shows its target branch and its current hold. An
editor can set, change or clear the target branch, both when adding a prerequisite and
afterwards. If the task changed in the meantime, the editor sees that the task was updated and
keeps the draft. ([#138](https://github.com/Denissvgn/WorkChord/pull/138))

### Clearer delivery holds

A delivery hold now says what is missing in each case:

- the target branch of the predecessor is unknown, so the merge cannot be checked on that
  branch (`merge_branch_unknown`);
- the predecessor was accepted, but its acceptance no longer matches its current version, so
  the task waits until the predecessor is accepted again;
- the predecessor was canceled, so a replacement has to be recorded.

Each hold names the next owner and the next action. ([#129](https://github.com/Denissvgn/WorkChord/pull/129),
[#140](https://github.com/Denissvgn/WorkChord/pull/140))

## What changed for PMs and agents

### Skill packages

| Role package | Version in this release | Version in 1.9.0 |
| --- | --- | --- |
| `workchord-pm` | 1.21.6 | 1.21.5 |
| `workchord-worker` | 1.20.3 | 1.20.3 |
| `workchord-reviewer` | 1.8.5 | 1.8.5 |

The skill catalog is at version 1.23.6. The PM package now names one actor and one set of
tools for GitHub catch-up and target branches: the PM agent runs catch-up and records or
retargets a prerequisite's branch, and a person does the same from the task page. The guidance
for an observed merge explains that acceptance is kept unless the head moved after acceptance,
and that one catch-up records every linked pull request.
([#140](https://github.com/Denissvgn/WorkChord/pull/140))

### MCP tools and REST route for GitHub and target branches

Agents can reconcile and catch up GitHub pull requests and manage delivery prerequisites
through MCP tools. Each tool calls the same service as its REST route, so the authority checks
are the same:

- `agent_get_github_reconciliation` reads the reconciliation of a task.
- `agent_run_github_catch_up` runs a catch-up over a task's linked pull requests.
- `agent_list_delivery_dependencies` lists a task's delivery prerequisites and their holds.
- `agent_add_delivery_dependency` adds a prerequisite, with an optional target branch.
- `agent_retarget_delivery_dependency` sets, changes or clears a prerequisite's target branch.

The new REST route is `PATCH /api/tasks/{task_id}/delivery-dependencies/{edge_id}`. Its body
takes `expected_version` and `target_branch`, and a `null` branch clears it. The route records
a `delivery_prerequisite_retargeted` event on the task timeline. Check the current API schemas
when you update a client. ([#134](https://github.com/Denissvgn/WorkChord/pull/134),
[#140](https://github.com/Denissvgn/WorkChord/pull/140))

## What changed for operators

### Self-hosted acceptance evidence store

The self-hosted acceptance profile stores its signed evidence in Versity S3 Gateway, which
replaces MinIO. MinIO no longer publishes the images that the acceptance profile pinned, so a
fresh host could not start acceptance. The Versity S3 Gateway image is digest-pinned, keeps
object-lock retention enforced even for its root identity, and runs with a restricted identity
for the acceptance job. ([#133](https://github.com/Denissvgn/WorkChord/pull/133))

The readiness endpoint answers only `{"status": ...}` in managed mode. Acceptance needs the
detailed payload, so it presents the `WORKCHORD_READINESS_DETAIL_TOKEN` value in the
`X-Readiness-Detail-Token` header. Other callers still receive the status only.
([#133](https://github.com/Denissvgn/WorkChord/pull/133))

Operators with an existing `server.env` must migrate it before running Docker Compose by hand.
The acceptance script does this on its next run, and the
[self-hosted adoption runbook](../runbooks/self-hosted-adoption.md) gives the command:

~~~bash
python3 "$WORKCHORD_INSTANCE_HOME/scripts/server/seed_adoption_env.py" \
  --migrate-env "$WORKCHORD_INSTANCE_HOME/.runtime/autonomy/server.env"
~~~

Acceptance receipts produced with MinIO (`implementation` `minio-s3-object-lock`) no longer
verify. Run acceptance again to obtain a current receipt. The evidence kept in the old
`workchord_autonomy_minio` volume is not read by the new store; remove that volume once its
retention has expired. The [acceptance runbook](../runbooks/self-hosted-server-acceptance.md#evidence-store)
describes the new settings.

### Documentation-only changes run documentation checks

A change that touches only documentation runs a short documentation check job instead of the
full CI pipeline. Anything else, including code, workflows, the agent skill sources, nested
Markdown and the documents that the release checks read, still runs the full pipeline.
([#144](https://github.com/Denissvgn/WorkChord/pull/144))

## Upgrade notes

### Database migrations

This release adds no migration. The schema head is the one that 1.9.0 introduced, the
delivery prerequisite target branch. Upgrading from 1.9.0 needs no database step beyond the
normal start.

### Self-hosted acceptance

Migrate an existing `server.env` in place as shown above, and rerun acceptance on the new
release before relying on its receipts. Earlier MinIO receipts no longer verify.

### Role skill packages

Reinstall `workchord-pm` at 1.21.6 and check its SHA-256 digest against the skill catalog
entry at 1.23.6. If your workspace already runs these versions, nothing needs to be
reinstalled. The setup steps for each runtime are in [agent team setup](../agent-team-setup.md).

### Frontend build

The frontend build no longer reads `tailwind.config.js`, `postcss.config.js` or
`autoprefixer`. A local customization of those files has to move to the Vite configuration.

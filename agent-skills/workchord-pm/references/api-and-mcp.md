## Connect without Exposing Secrets

Use runtime configuration such as:

```text
WORKCHORD_BASE_URL
WORKCHORD_API_PREFIX=/api
AGENT_API_KEY
MCP_AGENT_API_KEY
```

For REST agent routes, send the real actor key in `X-Agent-API-Key`. For HTTP MCP at `/api/mcp`, send `Authorization: Bearer <actor-key>` or `X-Agent-API-Key` when the client supports it.

Never put key values in this skill, a prompt, task description, event, project update, artifact, URL, command output, or source-controlled file. Never use the bootstrap key as a normal PM or MCP identity.

Ready filters remain compatibility-only. For exact worker state use
`/api/agent/me/work`; for complete secured context use
`/api/agent/tasks/{task_id}/context?assignment_id={id}`.

`GET /api/agent/me/work` accepts `limit` and an opaque cursor, returns compound
`pagination` metadata for ready and blocked assignments, and supports a private
weak ETag with `If-None-Match`/`304`. `GET /api/agent/me/reviews` and
`GET /api/agent/recovery` accept the same bounded pagination inputs and return
`{items, pagination}`. Discard a cursor and restart from the first page after
`409 stale_cursor`.

## Use the Application Planning API Carefully

The application REST API exposes the planning operations below, but a normal agent key is not automatically authority to call them. Confirm the deployment's session and authorization contract first. Do not copy a browser session token into agent configuration.

### Outcome and timebox

- Use `GET|POST /api/initiatives` and `GET|PUT|DELETE /api/initiatives/{id}` for authorized initiative CRUD.
- Use `GET|POST /api/projects` and `GET|PUT|DELETE /api/projects/{id}` for authorized project CRUD.
- Use `GET|POST /api/projects/{project_id}/milestones` and `PATCH|DELETE /api/projects/{project_id}/milestones/{milestone_id}` for milestone control.
- Use `/api/projects/{project_id}/releases` and `/api/releases/{release_id}` for release records.
- Use `/api/projects/{project_id}/summary`, `/tasks`, `/iterations`, and `/updates` for project control context.
- Use `GET|POST /api/calendars`, `GET|PUT|DELETE /api/calendars/{id}`, `GET /api/calendars/{id}/working-days`, and `POST /api/calendars/{id}/import-holidays` for calendars.
- Use `GET|POST /api/iterations`, `POST /api/iterations/series`, and `GET|PUT|DELETE /api/iterations/{id}` plus `GET /summary` for timeboxes.

### Team and capacity

- Use `/api/team-member-profiles` and `/api/team-member-profiles/{profile_id}/skills` for reusable capability profiles.
- Use `/api/iterations/{iteration_id}/team` for iteration capacity rows.
- Use `/api/team-members/{member_id}/capacity`, `/workload`, and `/vacations` for assignment evidence.
- Use iteration team/vacation import only through the explicit import routes.

### Intake and tasks

- Use `/api/triage` plus item duplicate-suggestion, classify, recommendation, draft, update, accept, decline, snooze, mark-duplicate, and convert routes for full intake control.
- Use `/api/iterations/{iteration_id}/tasks`, `/api/tasks/{task_id}`, dependency, reorder, move, bulk, timeline, and status routes for authorized planning operations.
- Supply `expected_version` for task updates and status changes whenever supported.

### Schedule, verification, and reporting

- Read `/api/iterations/{iteration_id}/gantt` before and after scheduling.
- Prefer the agent planning preview/apply pair. Treat the application
  `POST /api/iterations/{iteration_id}/schedule` route as a legacy direct
  mutation and do not use it as an agent-side preview substitute.
- Read `/api/tasks/{task_id}/timeline` and status history for verification.
- Use `/api/agent/projects/{project_id}/updates` or
  `agent_create_project_update` with `reports:write`, evidence, required
  rationale/correlation, and an idempotency key. The browser route remains
  session-attributed.

Never downgrade to an application route merely because MCP lacks a feature. Obtain the required human/session authority or stop with a clear handoff.

- complete task brief and dependency states;
- atomic begin/submit plus typed failure/cancel;
- claim ID and fencing generation on worker writes;
- durable idempotency and stable conflict metadata;
- independent review verdict, rework, and recovery operations.

If any required feature is absent, return to supervised v0 for that workflow.

## Supply Concurrency and Audit Fields

For task mutations, use the latest returned `version` as `expected_version`. Claims, renewals, releases, schedule/status changes, and other task mutations can change it; never reuse an earlier cached version.

For retryable mutations, derive one stable idempotency key from the logical operation, target, and workflow/run identity. Reuse it only for the identical request. Use a new key after changing the request or re-evaluating a conflict.

Every PM setup REST command requires `Idempotency-Key`, `X-Agent-Rationale`,
and `X-Correlation-ID`; MCP equivalents require the matching
`idempotency_key`, `rationale`, and `correlation_id` arguments. The exact
receipt records all three with the actor and authoritative result. Project,
iteration, profile, member, and vacation models currently expose no optimistic
version token, so do not invent one: use exact idempotency, serialize related
commands, and re-read authoritative state. Schedule apply is stricter: submit
both the complete task-version map and `expected_input_digest` from a fresh
preview. The digest changes with iteration/calendar, capacity, vacations, task
scheduling fields, dependencies, or applicable scheduling rules.

Propagate safe trace fields consistently:

- `trace_id` for the end-to-end planning or delivery decision;
- `span_id` for one operation;
- `correlation_id` for the source request, issue, release, or orchestration message.

Keep event payloads bounded. Include summary, rationale, evidence links, next steps, and owner; omit secrets and large raw logs.

The recovery read is also a write token: submit its complete live-assignment
IDs, running-run IDs, claim generation, and task version unchanged. A mismatch
means ownership changed and requires a new recovery read. Verification verdicts
must likewise use an eligible current verifier assignment whose task version
still matches and whose `not_before` time has arrived.

## Handle Responses

| Response | Action |
| --- | --- |
| `200/201` | Re-read the affected state; do not rely solely on the mutation response for cross-object consequences. |
| `400/422` | Correct the payload or planning invariant; do not retry unchanged. |
| `401/403` | Stop and report the required scope or identity action; never search for another key. |
| `404` | Refetch the parent/list context and verify scope; do not recreate automatically. |
| `409` version/claim/assignment/queue conflict | Refetch authoritative state, re-evaluate, and use a new logical action only if still valid. |
| `409 stale_cursor` | Discard the cursor and restart that read at its first page. |
| `409` duplicate conversion/idempotency replay | Confirm the existing result matches the intended action before treating it as success. |
| `429/5xx` or timeout | Retry only supported idempotent operations with the same key and bounded backoff; otherwise read state first. |

Preserve structured conflict codes and current-state metadata. Do not collapse them into a generic “failed” event.

## Recognize Supervised-v0 Gaps

An older or partially upgraded deployment may not provide:

- an authenticated capabilities handshake;
- actor role/profile binding or a PM-visible enabled actor roster;
- durable actor task assignments and per-actor queue order;
- authoritative `/me/work` current/next selection;
- REST agent task context, my-claims, or my-runs;
- atomic fenced begin/submit/fail operations;
- role-specific PM, worker, and verifier scopes;
- MCP parity for team, calendar, capacity, schedule/Gantt, pipeline, runs, complete Triage, and project updates;
- a typed verification queue/verdict, ordered rework handoff, or stale-work reconciler.

The stable 1.0 role requires these capabilities for unattended operation. State
any missing live feature in a handoff and fall back to supervised v0. Do not
compensate with local queue ranking, shared actor keys, speculative claims,
self-review, unrecorded project updates, or unattended parallel execution.

The separate supervised-v0 claim/run/event/finish primitives are compatibility
operations, not the v1 transaction contract. They do not promise v1 exact
receipts or terminal-race handling; after any timeout or ambiguous terminal
write, read task, claim, and run state and hand off reconciliation.
